# Potential 2.0 — legacy 74 / 68 root-cause audit

**Status:** read-only provenance finding. No live save migration or numerical V2 seed is approved by this document.

## Executive finding

The saved 74 / 68 split is **not evidence of two competing valid evaluations**.

- The nested `development.potential = 68` is the stale original development baseline. The historical development initializer falls back to current OVR when a root potential does not yet exist; the career's preserved starting OVR is 68.
- The root potential values that later became 71, 73 and 74 were generated by the legacy live weekly evaluator's automatic young-player floor of **current OVR + 2**.
- Historical Travel/career synchronization could carry the newer root `potential` into the lightweight UI snapshot while leaving the nested `development` object stale.
- Before the September 2 canonical-career identity fix, a missing/stale lightweight career ID could make the UI synchronization fallback rebuild a career roster record from that split snapshot. Canonicalization preserved the stale nested object over the root-derived default. The next legacy weekly evaluation therefore saw 68 again.
- Current production no longer uses that identity lookup path: it resolves the permanent roster career player first. The merged Potential V2 release guard also refuses to evaluate any unresolved root/development mismatch.

Therefore **neither 68 nor 74 should automatically become the Potential 2.0 canonical seed**. 68 is a stale initialization artifact; 74 is a forced legacy OVR-floor artifact. A V2 seed must be reviewed from independent career evidence, not selected by field precedence.

## Historical code chain

### A. Development baseline could start at OVR

Before the later weekly system existed, `createDefaultDevelopmentState(player)` selected nested potential from:

`player.potential || player.overall || 60`

The fresh career flow did not need a separately established root potential to initialize development. With the preserved starting OVR of 68, a nested 68 baseline is consistent with the historical initializer.

### B. Legacy weekly potential imposed an OVR floor

Commit `4466aa38f66e` introduced the old weekly dynamic-potential evaluator. Its canonical input priority was nested development potential before root potential, and for players age 23 or younger it imposed:

`minimumPotential = overall + 2`

It then wrote that result to both root and nested potential. On an uninterrupted single player object that would have synchronized the two fields.

### C. Travel root synchronization was deliberately selective

Historical `travel-hockey-canonical-ui.js` synchronized identity, OVR, attributes, age and **root `potential`** from the permanent roster player into the lightweight world/Game snapshot. The selected key list did **not** include `development`.

That made a split snapshot possible after a weekly floor update:

- root snapshot: new 73/74
- nested UI development snapshot: old 68

### D. Old career lookup could fall through to rebuilding from the split snapshot

Before the canonical-career identity repair, `syncCareerPlayerWithWorld()` attempted only:

`WorldEngine.getPlayerById(careerPlayerId)`

If the lightweight snapshot had a missing/stale ID, the lookup could miss the permanent career roster record and call:

`WorldEngine.upsertCareerPlayer({ ...Game.player, ... })`

The September 2 canonical-career repair explicitly changed this path to resolve `WorldEngine.getCareerPlayer()` first and also repaired the root snapshot's permanent identity. The associated historical diagnostic documents the practical failure mode: a stale/missing snapshot identity could cause the next UI sync to create another career-player record.

### E. Canonicalization preserves the stale nested override

When a fallback rebuild starts from a snapshot with root POT 74 but `development.potential = 68`:

1. default development sees root 74;
2. `ensureCanonicalPlayerContract` merges the saved `player.development` afterward;
3. stale nested 68 overrides the default 74;
4. the rebuilt object is root 74 / nested 68 again.

The next old weekly evaluator prioritizes nested 68, applies OVR+2, and can emit another 68 → 74 update. This is exactly the repeated pattern preserved in the private save.

## Reproducible regression

`tools/potential-v2-root-cause-provenance.test.js` does two things:

1. **Synthetic/history mode:** reads the exact historical Git revisions, asserts the source fingerprints above, and replays the root-only-sync → stale nested rebuild → OVR+2 loop without IndexedDB or a user save.
2. **Optional private mode:** accepts a local backup path and verifies only aggregate provenance: 20/20 restart-from-68 beats, 20/20 OVR+2 matches, archived 69/71 and 72/74 pairs, empty potential history and unchanged source bytes.

The CI workflow fetches full Git history but **never receives a private backup**.

## Migration consequence

Potential 2.0 must treat the current conflict as **legacy provenance contamination**, not as a choice between two equally authoritative values.

Do not:
- pick 74 because it is the larger/root value;
- pick 68 because it is nested under `development`;
- average the two;
- replay the old OVR+2 floor;
- infer a new number from current 72 OVR alone.

The next stage is a separate read-only **canonical seed review** using clean evidence such as age-appropriate historical performance, development trajectory, competition context and uncontaminated comparable players. That review may conclude that a numerical seed should be above, below or between the old artifacts; this audit itself makes no numerical recommendation.

## Live-safety status

The production legacy-writer guard is already merged and blocks the unresolved conflict from weekly mutation. Full Potential 2.0 remains offline. No save migration, XP rewrite, history rewrite, root/nested synchronization or numerical rerating is authorized by this audit.
